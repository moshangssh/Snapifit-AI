# 「今天还能吃什么」从三方案收敛为「3 个吃法挑一个」

「今天还能吃什么」原本输出两套并列产物:3 套覆盖全天剩余餐次的**方案**(steady / craving / high_protein),外加一份 3–8 个**单品**清单,UI 用分段控件切换。我们决定把它收敛成**一份恰好 3 个「吃法」的平铺清单**——每个吃法是只针对下一顿主餐、自带份量、合剩余预算的互斥备选,挑一个即可;其中**始终有一条由服务端打标的「补蛋白之选」**,保证用户即使在表达放纵口味时也能够到当日剩余蛋白目标。

这么做有两个理由:一是「整天 × 3 套 + 单独单品区」对一个即时决策卡片**信息过载**(用户口中的「点多」);二是「每套都要重铺全天剩余餐次」这个结构会**诱发 LLM 把已经吃过的餐次又规划进去**,而 plan 总热量是跟「已扣除已吃」的剩余预算比对的,导致预算口径不一致、误报超标或挤压真正剩下的餐。改成「单顿、挑一个」后每条天然自洽(每条 ≤ 剩余预算即可),这类 bug 没有发生空间。

## Considered Options

- **砍数量保结构**(整天方案降到 1–2 套):仍保留「重铺全天」的结构,bug 温床还在。
- **砍结构保数量**(每套只管下一餐但仍成套):比纯单品多了搭配价值,但每条偏重。
- **两者都砍(选定)**:删掉「整天方案」概念,合并成一份挑一个的吃法清单。
- 在合并后,曾考虑给每条固定意图标签(高蛋白/解馋/均衡),但与「窄口味场景下构成动态变化」冲突,改为**只明牌补蛋白之选一条**,且由服务端按校验结果打标,而非让 LLM 自我声明,避免标签与真实营养数字脱节。

## Consequences

- 持久化结构 `MealPlanSuggestion` 移除 `plans`;`MealPlanType` / `MealPlanOption` / `MealPlanMeal` / `MealPlanDisplayMode` 退役。历史 `DailyLog.mealPlanSuggestion` 中的旧 `plans` 视为当天临时数据,读取时容忍、不渲染,不做迁移。
- `validateMealPlanBudget` 从「按 plan 类型校验」改为「每条 ≤ 剩余×1.05 且至少一条蛋白达标」。`calculateMinHighProteinGrams` 中按整套热量定的 0.35 上限需按单顿重新调参。
- 放弃了「全天编排 / 多套完整方案」的能力——这是刻意的取舍,换取简洁与预算口径的一致性。
